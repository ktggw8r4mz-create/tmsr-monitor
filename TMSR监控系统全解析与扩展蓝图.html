大白话版：这套系统到底在干什么

一句话：它是一台「链上雷达」。每 24 小时自动扫描一次 TMSR 项目全部关键钱包和合约状态，任何风吹草动——有人提币、开关变化、价格异常——立刻把警报发到你手机 Telegram 上。

好比给这个项目装了「监控摄像头 + 自动报警器」。盯的不是小偷，而是三件事：

① 钱在谁手里？——金库 18.89 亿枚代币还在不在，有没有被 owner 悄悄转走；

② 钥匙在谁手里？——买入开关、销售开关、提现后门有没有被打开或关闭；

③ 价格合不合理？——官网售价 0.05 与市价 0.186 的倒挂有没有扩大，LP 有没有被撤。

你不必懂 Solidity 或 RPC——系统把链上原始数据翻译成了「健康度 28/100 + 5 个红灯 + 5 项风险预测」，你只需要看颜色：红 = 危险，橙 = 警惕，绿 = 正常。

运行逻辑（专业层）：一轮完整执行

触发：macOS launchd 每 24 小时唤起 run_all.py，四步串并行执行，任一步失败不影响后续（RPC 限流自动下一轮重试）：

Step 1  monitor_all  ‖  tmsr_monitor   （并行，各约 1-3 分钟）
        └─ 16 地址×4 资产快照      └─ 16 项指标 + 合约状态
Step 2  predict.py                 （读两份快照 → 5 项风险概率 → predict.json）
Step 3  telegram_notify.py         （与 baseline 对比 → 有变动则推送 → 更新 baseline）

变动检测三通道（notify 内核）：

  1. 状态 diff：buyEnabled / salePrice / totalOrders / salePaused / treasuryPaused / 锁仓参数 / 税率等 12 个键，前后值不一致即报；
  2. 价格 diff：DEX 价格变动幅度 ≥ 3%（config 可调）即报；
  3. 余额 diff：16 地址 × 4 资产逐项对比，TMSR ≥1 / USDT ≥1 / LP ≥0.1 / BNB ≥0.01（阈值可调）即报。

防重复推送机制：每轮无论是否推送都更新 baseline.json——把"当前状态"固化为"下次对比基准"。链上连续小幅波动只会在累计超过阈值时报警一次，不会刷屏。

预测逻辑：5 项风险事件的概率评分

每个事件 = 一组可观测信号的加权打分（0-100），反映「结构性概率」——即当前资金面/结构面下事件发生的容易程度，不是时间点预测：

事件评分核心输入信号
P1 开放销售被套利抽干95售价倒挂幅度（-73% 得 70 分）+ 销售未暂停 + 0 订单（随时可开）
P2 owner 后门提币75金库 18.89 亿 + 提现 3 万 + 光能 USDT，无时间锁基线 35 分
P3 撤池归零100LP 占比 99.95% 未锁定（>90% 即 50 分）+ 售价倒挂追加
P4 涡轮偿付缺口10未兑订单 0（基线 10 分）；reserved 接近余额时抬升至 50-90
P5 参数突变30买入开关已关闭 15 分 + 销售未暂停 10 分

综合风险 = 五项均值（当前 62/高）。信号缺数据时该项不参与扣分/加分，避免假象；完整公式见 predict.py。

A · 高频警报层（P0，最值得立刻做）

问题：当前 24h 一轮，owner 提币、撤池这类"瞬间致命"事件最多滞后一天。而它其实可以几乎实时——关键信号只需 5-6 个 eth_call。

方案：新增 fast_alert.py + 独立 launchd 任务（每 60-120 秒）：

  1. 5 个合约 owner 地址的 TMSR/USDT 余额（后门提币 = 余额骤降）；
  2. initialRecipient 的 LP 余额（撤池前兆 = LP 减少）；
  3. buyEnabled / salePaused / treasuryPaused 三个开关（机制状态突变）；
  4. DEX 池储备比值（价格崩盘 / 巨量买入卖出）。

收益：致命事件通知从「滞后 24h」降到「滞后 2 分钟」。成本几乎为零（复用现有 RPC 与推送通道）。

B · 交易级监控（P1，需 BscScan API Key）

拿到 BscScan API Key（免费，注册即得）后可解锁公共 RPC 做不到的日志回溯：

  1. 转账事件流：实时拉取 TMSR Transfer 日志，监控每一笔进出（谁 → 谁 → 多少）；
  2. 大额异动榜：单笔超过阈值（如 5 万 TMSR）的转账自动推送 + 归集到地址画像；
  3. 撤池前兆：Pair 的 Sync/Burn 事件——LP 减少斜率检测，提前于价格反应；
  4. 闪电贷 / MEV 检测：借出-买入-卖出-还款在 1 区块内完成的模式识别（Pancake 池的典型攻击路径）。

C · 历史与画像（P1）

  1. 持币分布：TOP 100 持仓地址 + 筹码集中度（前 10 占比），识别"巨鲸"动向；
  2. owner 变更史：合约 owner 是否换过手、换手频率（权限风险的时间维度）；
  3. 24h 量价：成交量、换手率、价格波动区间，判断真实市场热度 vs 自买自卖；
  4. 部署者画像：创建合约的地址还部署过什么（多项目关联，识别批量发币团队）。

D · 运营事件信号（P1）

监听合约事件（需 archive 节点或 BscScan Logs API）：

  1. openSale / 销售暂停——开放销售 = P1 抽干风险从"可能"变"正在发生"；
  2. 订单创建 / 兑付——涡轮偿付缺口实时核算；
  3. 税率 / 豁免名单变更——owner 突改参数的原始证据；
  4. 金库注资 / 提现发放——机制是否按白名单运转。

E · 数据资产化（P2，免费但长期价值最高）

  1. SQLite 历史库：每一轮快照落库，形成 30/90/180 天时间序列；
  2. 趋势图：健康度走势、LP 锁定率变化、价格与偏离的历史曲线——"风险是积累出来的"；
  3. 预测回测：记录 P1-P5 评分与后续 7 天实际事件，量化这套规则引擎的命中率，持续校准阈值；
  4. 报告生成：每周自动生成「风险变化周报」推送到 Telegram。

F · 通知渠道扩展（P2）

分级通知Info（余额微动）/ Warning（开关变化）/ Critical（后门提币、撤池）
多渠道邮件、钉钉/企微 Webhook、Server酱（微信）、Telegram 群广播
定时日报每天 9:00 推送「昨日快照摘要」：健康度、5 项预测、变动清单

G · 多项目复制（P2）

把地址表、合约方法、阈值抽成 project.json 模板：新项目只需填一份配置（5 个合约地址 + owner + 池子），10 分钟接入同一套采集/预测/推送/可视化体系——你的监控体系从此是「平台」而非「单项目脚本」。

H · 合规与风控增强（P2）

  1. 舆情监控：项目方社群（Telegram/Discord/Twitter）关键词扫描——跑路前兆（删群、禁言、FUD 回应）；
  2. 动态风险评分：把舆情、交易、持仓集中度并入现有评分，形成多因子风险模型；
  3. 事件时间线：重大链上事件 + 项目方公告对齐，还原"宣传 vs 实际"的实时差距（本审计的核心方法论）。

I · 远期 AI 化（P3 探索）

  1. 异常模式识别：规则 + 统计基线结合（如"正常波动区间外的持续小额提现"= 洗钱/准备跑路模式）；
  2. 事件因果链：从"owner 授权变更 → 大额转账 → LP 卖出"串联为风险剧本，推送时给出上下文而非孤立数值；
  3. 决策建议：风险事件触发时自动生成「该做什么」（离场/核实/等待）清单，附证据链。

当前局限（诚实声明）

  1. 公共 RPC 无法回溯历史日志：24h 交易量、owner 变更史、转账明细需要 BscScan API Key 或 archive 节点——这是历史类监控缺口的唯一原因；
  2. 24h 粒度：owner 提币这类事件最多滞后 24 小时通知（详见扩展 A：高频警报层）；
  3. 预测为规则推断：基于资金面/结构面信号，非机器学习模型，不含情绪/舆情因子；
  4. 只读不写：系统只观察和报警，无自动交易、无对冲能力。
